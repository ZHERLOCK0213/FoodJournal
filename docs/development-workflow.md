# FoodJourney 开发流程

本流程面向项目维护者与协作者。目标是让每次变更都能说明问题、实施范围、验证证据和仍存在的限制。

## 从问题到交付

1. **核实问题**：记录分支、提交、运行版本、输入与复现步骤，区分当前行为和历史描述。
2. **定义范围**：明确使用者、预期结果、异常状态及验收标准；区分事实、估算与设计判断。
3. **设计方案**：需要交互比较时先制作小原型；需要定量结论时先检查来源与单位。
4. **小范围实现**：保持数据与界面职责清楚，避免同时加入不相关重构。
5. **验证结果**：静态检查、针对性测试、界面体验分别记录；未执行的环节明确标注。
6. **审阅与交付**：核对最终差异，更新相关文档；代码合并与正式发布分别管理。
7. **复盘**：记录实际效果、剩余问题和可复用知识。

## 验证与测试隔离

当前静态检查已发现部分单元测试默认创建 `FoodLibrary()`，调用添加食物后会写入测试设备的最近使用记录。回归前应改为注入 `FoodLibrary(storage: MemoryFoodLibraryStorage())` 或等效隔离实例，并使用独立的测试模拟器。

UI 测试通过 `-uiTesting` 隔离相关本机数据，但这不能自动保证所有单元测试也完成隔离。历史布局测试还包含与当前气泡文案不符的断言，需要先依据产品行为更新。

| 变更 | 必要检查 |
| --- | --- |
| 文档 | 相对链接、状态、来源、隐私信息与差异 |
| 食物数据 | 原始记录、单位、做法、换算、缺项与受影响样例 |
| 计算或持久化 | 边界、错误路径、快照、版本和存储失败 |
| 交互或画布 | 主流程、异常状态、字号、读屏、动态效果与布局 |
| 发布候选 | 真机、系统与设备范围、隐私、签名、材料与支持入口 |

测试记录包含提交、环境、通过/失败/跳过及定向复测情况。全量存在失败后再定向复测通过，应如实分开记录；历史结果文件未随仓库提供时，不将记录称为可下载的验证报告。

## AI 辅助协作

AI 可以帮助检索、提出方案、编写代码或发现问题。维护者仍负责理解需求、确认来源和验收成果。可独立的工作按文件或模块拆分，最终统一核对差异、接口和结论。

工作记录应能脱离具体工具与个人环境，被其他协作者理解和复现。对外说明应清楚区分 AI 辅助完成的内容、人工检查和实际运行结果。

## 学习方式

以一个可以完成的小任务为单位：先理解需求和现有实现，再修改关键部分，解释结果，最后验证并复盘。学习成果是能独立说明和复现，而不是只保留一份生成代码。

## 版本与维护

版本说明记录使用者能感知的变化及数据迁移影响。食物或科普内容修正应保留来源与适用范围；本机数据格式变化需要兼容策略。正式发布前使用 [发布准备](release-readiness.md)，当前状态见 [项目状态](project-status.md)。
