# FoodJourney 项目概览

更新：2026-09-25。

## 项目目标

FoodJourney 希望用互动示意帮助普通成年人理解食物的消化过程，并作为从需求、设计、开发、验证到发布维护的完整实践项目。

面向对消化好奇的成年人，同时关注有慢性病史读者可能产生的理解偏差。首发计划为中国大陆、iOS 独占，优先验证山姆会员的食品理解场景；这一选择不表示已获得山姆合作、数据接入或品牌授权。当前不提供诊疗、疾病风险预测或个人营养处方。

项目以持续学习和可验收的小步迭代推进，尚无固定上架日期。功能状态见 [项目状态](project-status.md)，具体契约见 [产品规格](PRD.md)。

## 需要验证的价值

- 用户是否能通过一份食物理解器官之间的协作，而非只观看动画？
- 用户是否能分辨食物成分、一般生理机制与个人实际身体反应？
- 成分矩阵及来源是否帮助理解份量、做法和缺项？
- 用户是否有明确的再次使用场景？

目前已有维护者的功能体验记录，尚未形成独立目标用户研究或健康效果证据。上述问题是验证方向，不是已经实现的结果。

## 同类产品与差异假设

以下依据 2026-09-23 查阅的官方功能介绍，未实际操作这些应用；不代表功能准确性、留存或健康效果得到独立验证。海外产品用于任务比较，不表示其在中国大陆可用或已适配本地食品。

| 产品 | 官方描述的核心任务 | 对 FoodJourney 的启发与限制 |
| --- | --- | --- |
| [薄荷健康](https://www.boohee.com/) | 食物查询、餐食识别、饮食等健康记录和分析 | 仅有成分合计难以形成差异；需验证解释是否比增加记录负担更有价值 |
| [Yuka](https://yuka.io/en/app/) | 扫码、解释商品评分、类似替代推荐与历史 | 包装商品有明确的购买比较场景；当前尚无商品扫码与替代搜索 |
| [ZOE](https://zoe.com/en-gb/buymembership) | 餐食扫描、反馈和个性化饮食服务，可结合肠道检测 | 个人化需要额外信息与验证；学习偏好不能当作生理模型 |
| [BioDigital Human](https://www.biodigital.com/p/mobile) | 互动三维人体解剖、生理等主题探索 | FoodJourney 可尝试从熟悉的一份食物切入，而不是要求读者先选择抽象的人体主题 |

潜在强项是把食物成分与器官作用连起来，让读者能解释“为什么”。当前弱项是食品覆盖少、输入份量有成本、气泡内容差异有限、没有跨餐历史或留存证据。动画新鲜感与学习效果都不能自动推出长期使用。

“代谢报告”可能被误读为个人检测，需要通过内容边界和读者验证减少误解。界面入口应让读者理解各页用途，具体导航契约见 [产品规格](PRD.md)。参考 [Apple 标签栏指引](https://developer.apple.com/design/human-interface-guidelines/tab-bars)：标签栏承载顶层目的地，数量取决于内容与访问需要。

## 山姆商品场景：证据与假设

- **可核实事实：**山姆官方披露会籍、续卡率与活跃度上升，说明其既有会员业务活跃；这不证明会员会反复使用独立科普应用。[官方公告](https://www.walmart.cn/newsroom/1879.html)
- **接口边界：**已找到中国 [Retail Link 供应商系统](https://www.walmart.cn/retail/)和明确针对美国 1P 供应商的 [Walmart API](https://developer.walmart.com/suppliers/docs/get-started)，均需要相应资格或凭据。此次未找到可确认供独立开发者调用的中国山姆营养公共 API；不能据此断言非公开合作接口不存在。
- **未验证假设：**会员愿意使用本应用；健康关注意味着较强支付意愿；科普应用会促使非会员加入山姆。健康关注不必然意味着高收入，会员身份也不能代替需求验证。
- **品牌与数据条件：**已明确继续使用 FoodJourney 品牌，拟围绕山姆商品理解场景宣传。实际覆盖以已核对和可用的功能为准，不宣称官方合作。数据批量获取、缓存、再分发和更新方式仍需明确条件。

营养成分表可作为对应包装商品的数据来源，配料表主要用于了解原料，两者用途不同。企业可使用检测或配方计算取得标示数据，因此不必为每件商品自行送检，但仍需核对商品版本、单位、份量、售卖或冲调状态和录入结果；标签不提供的嘌呤不自行补成确定值。[国家卫健委说明](https://www.nhc.gov.cn/zwgk/zcjd/201402/6f68ec6692594cf28d190cb47b770c11.shtml)

候选试点先选 10–20 个有明确来源的常用商品，以人工核对的本地小目录验证问题。数量是控制工作量的建议，不是覆盖率或统计有效性承诺。得到使用价值证据后，再讨论数据授权、合作接口或授权文件导入；接口不是试点的前置条件。合作可能带来的商品评价独立性、渠道依赖和持续更新责任也需要评估。

## 使用场景与验证方法

长期使用的价值假设是帮助读者在购买、备餐或选择份量时解决具体疑问，动画用于解释原因。是否在吃饭时使用由读者选择，不以占用整顿饭或替代短视频为目标。

| 场景 | 原型任务 | 需要观察的证据 |
| --- | --- | --- |
| 一人吃饭 | 选择熟悉食品及自己的份量，查看一次改变份量带来的成分差别 | 是否能独立完成、是否看懂、哪些输入造成放弃 |
| 多人吃饭 | 选择一道共享菜了解机制；需要个人合计时明确自己的份量 | 是否误把全桌当个人摄入，是否能不暴露私人健康信息地使用 |
| 购物或备餐 | 对照两个具体商品及实际食用份量 | 是否解决原本存在的疑问，是否需要退出应用再找基础信息 |
| 再次使用 | 下一次遇到相同或新问题时自行打开 | 真实触发及未复访原因，而非只记录“愿意以后使用” |

初期可邀请少量目标读者完成任务，记录理解偏差、完成路径与复访原因，不用便利样本估算市场规模或正式留存率。科普理解、使用行为与健康结果分别评估。

饭点提醒只提供再次打开的线索，不能代替使用价值；是否开启提醒也不是留存或健康收益的证据。器官造型、动作和叙事可能帮助建立品牌识别，仍需用读者能否解释机制、理解食物差异及持续使用的表现验证。交互契约见 [产品规格](PRD.md)，实现与验收范围见 [项目状态](project-status.md)。

第一批五款商品的原始标签与换算例子见 [标签试点练习](learning/sams-label-pilot.md)。先理解基准、单位和缺项，再安排本地 SQL 保存练习。

## 学习与交付物

| 方向 | 项目中的练习 | 可检查的成果 |
| --- | --- | --- |
| Axure RP 11 | 食物编辑、空状态、异常流程 | 可试用的交互原型与验收说明 |
| HTML / CSS / JavaScript | 科普素材页、介绍与支持页面 | 响应式布局、基本交互、可访问性检查 |
| SQL / MySQL | 食物、成分、来源、版本的数据练习 | 表结构、查询、约束与迁移演练 |
| Swift / SwiftUI | 输入、状态、快照、计算、界面与持久化 | 可解释的实现与针对性验证 |
| Python | 数据缺项、单位和异常值检查 | 可复现脚本与问题清单 |
| 项目管理 | 需求、取舍、版本、缺陷与复盘 | 有范围、证据和责任归属的交付记录 |

学习材料围绕真实问题安排。SQL 练习不要求立即把应用接入服务器，Python 也不是当前原生界面的替代语言。

数据存储、程序测试与科学有效性是不同问题：SQL 管理结构化记录，测试验证程序是否遵守规则，内容审阅判断来源与规则是否适用。无需收集世界上全部食物才能使用数据库，也无需部署数据库才能对已有食品做计算测试。当前保持本地架构，付费云服务与数据库采购尚未进入范围。

## AI 辅助开发与未来探索

AI 辅助开发不等于应用已具有 AI 功能；协作与验收方式见 [开发流程](development-workflow.md)。

“自然语言菜单转食物草稿”是尚未实施的探索方向：先返回可确认的食物、份量及不确定项，再由确定性数据和计算生成展示。它不是已排期功能，也不应直接生成营养数值或医疗结论。

如后续开展该实验，应另行设计中文输入样本、人工标注、错误处理、成本预算与隐私边界；是否需要服务端由实际需求决定。

## 成本与维护

除实现时间外，还需要为内容来源核对、专业审阅、真机验证、无障碍、发布材料和用户支持留出资源。新增账号或在线服务后，还会产生数据迁移、权限、安全与持续运行成本。

本地版本也需要内容纠错、兼容更新和数据恢复策略。路线候选见 [项目路线图](project-status.md#下一步)。
