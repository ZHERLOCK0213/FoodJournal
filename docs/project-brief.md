## 一、项目定位

### 1. 一句话愿景

让普通人用一段好看的互动动画，理解一份食物在消化与代谢中经历了什么；把抽象的营养知识变成可感知、可分享的体验。

### 2. 要解决的问题

营养成分表、科普文章和短视频往往告诉用户“有什么”，却很少让人直观看到“它在身体里经历什么”。当用户好奇一碗饭、西兰花或三文鱼时，FoodJourney 提供一个低门槛、非医疗化的预演入口。

### 3. 目标用户与 Jobs-to-be-Done

| 用户 | 触发时刻 | 希望完成的事 |
|---|---|---|
| 饮食与消化好奇者 | 吃饭前、刷到饮食话题时 | 用几十秒看懂食物在体内的旅行 |
| 关注碳水、嘌呤或热量的人 | 犹豫要不要加一份食物时 | 看一份**教育性、相对的**营养与代谢路径，不接受诊断 |
| 内容平台观众 | 看到一段录屏时 | 一眼理解“这是什么 App”，并想点名下一种食物 |

### 4. 核心差异化

- 动画不是报告的装饰，而是产品本体。
- 用“食物 → 成分 → 路径 → 去向”的因果链表达营养知识。
- 把 LLM 放在理解用户语言的位置，把营养数据、计算与动画放在可审核的确定性系统里。

## 二、产品原则与边界

### 产品原则

1. **动画优先**：首个 Demo 的完成标准是录屏有吸引力，而不是功能数量多。
2. **事实与生成分工**：数值、食物匹配、动画规则由数据与程序决定；LLM 只做语言理解和教育性表达。
3. **用户最终确认**：LLM 对食物、份量或烹饪方式有不确定性时，必须展示候选并让用户修改后再预演。
4. **本地优先，按价值接后端**：手动选食物的核心体验继续离线可用；只有“自然语言点餐”这一明确价值进入产品后，才增加最小 AI 服务。
5. **不把科普说成医疗结论**：不诊断、不预测疾病风险、不生成治疗或个体化处方。

### 不做什么

- 不以“内脏能力”“滞留量”“血糖数值”判断某个用户的身体状态。
- 不把用户的慢性病、检验单、症状或用药发给模型。
- 不让 LLM 直接生成营养数值、消化机制或医学建议后展示给用户。
- 不为了“AI 味”过早引入多 Agent、RAG、向量数据库或长期记忆。

## 三、版本路线与成功信号

| 阶段 | 目标 | 成功信号 |
|---|---|---|
| A. 视觉 Demo（当前） | 米饭、西兰花、三文鱼的完整动画 | 录屏不需讲解也能看懂“食物在旅行” |
| B. 可用原型 | 连续进食、删除、重置、报告稳定 | 主流程自动化测试可重复通过 |
| C. 可信内容 | 建立食物来源台账与教育化报告 | 每个展示量能说明其来源或“示意”属性 |
| D. AI 菜单翻译 POC | 自然语言转可确认的食物草稿 | 小样本中食物匹配正确、遇到模糊表达会追问 |
| E. 上架准备 | TestFlight、无障碍、隐私与商店页 | 获得真实反馈，能安全稳定发布 |

> AI 不是 A 阶段的阻塞项。先用手动食物 Chip 打磨“预演值得看”的体验；否则 AI 只会把不清晰的核心体验包装得更复杂。

## 四、核心工作流

### 1. 当前主流程

```text
选择内置食物 → 确认一份 → 消化动画 → 教育性报告 → 分享 / 再试一种食物
```

### 2. 目标 AI 主流程（提议）

```text
用户说/输入“晚饭半碗米饭、番茄炒蛋，少油”
    ↓
LLM 只输出结构化「食物草稿」与不确定项
    ↓
用户确认或修改食物、份量、做法
    ↓
FoodCatalog 匹配权威来源的标准食物数据
    ↓
确定性消化计算与动画引擎
    ↓
教育性报告；可选 LLM 用受限事实卡生成简短解说
```

这条链的关键是：**LLM 不能直接跳到报告。** 它输出的是可见、可编辑的草稿；动画和数值仍然可测试、可追溯。

## 五、功能模块

| 模块 | 用户价值 | 当前状态 | 设计要点 |
|---|---|---|---|
| 消化预演画布 | “看见”食物的路径 | 已有 | 优先 3 种食物的镜头质量与标签可读性 |
| 当前顿会话 | 试多种食物并看累积结果 | 已有 | 删除、重置、串行动画需可靠 |
| 教育性报告 | 知道成分去了哪里 | 已有，待收敛 | 用相对比较和科普说明替代个人健康断言 |
| 食物数据台账 | 让展示可信 | 待建 | 来源、版本、100g 口径、别名、可视化配置分离 |
| **AI 菜单翻译** | 不用在 Chip 里翻找食物 | 提议，D 阶段 POC | 文字/语音菜单 → 可确认草稿；失败可退回手动选择 |
| AI 科普解说 | 让报告更易读 | 后续评估 | 只基于应用提供的事实卡，短文本、可替换、无医疗建议 |

### AI 菜单翻译的输入输出契约

输入：`“晚饭吃了半碗米饭，番茄炒蛋，少油。”`

模型输出应类似：

```json
{
  "items": [
    {"candidate": "米饭", "portion": "半碗", "confidence": "medium"},
    {"candidate": "番茄炒蛋", "cooking": "少油", "confidence": "medium"}
  ],
  "questions": ["番茄炒蛋大约是一小盘还是一大盘？"],
  "medicalAdvice": null
}
```

随后由 FoodJourney 选择本地已审核的食物条目与份量规则。任何未知食物、复合菜、份量或做法都必须标成“待确认”，不能伪装成精确识别。

## 六、技术架构

### 1. 当前架构（继续保持简单）

```text
SwiftUI Views
    ↓
LiveSessionViewModel（交互与动画状态机）
    ↓
DigestionSession（单顿计算）
    ↓
FoodCatalog / FoodDatabase（本地、可追溯数据）
    ↓
UserDefaults（仅展示偏好）
```

### 2. 仅在 AI 菜单翻译上线时增加的最小服务

```text
iOS App
    ↓ HTTPS
AI Gateway（保护密钥、限流、版本与审计）
    ↓
结构化输出 LLM
    ↓
Food Canonicalizer（别名 → 已审核 FoodCatalog 条目）
    ↓
返回可确认 MealDraft；不返回医疗结论
```

- **为什么需要服务端**：产品不能把模型 API 密钥放进 iOS App；还需要限流、成本控制、模型版本管理和安全过滤。这是清晰的用户价值与工程必要性，不是为了“架构看起来高级”。
- **为什么先不做 RAG**：早期只有少量、人工审核的食物与科普卡片时，直接随请求携带相应事实更稳定、更容易审查。食物与知识条目规模变大、需要自动检索引用时再评估检索层。
- **为什么先不做 Agent**：当前是一条短、确定的转换链，不需要模型自主拆解并执行复杂任务。多 Agent 只会增加不可预测性、延迟和调试成本。
- **隐私默认值**：不上传问卷健康信息；菜单文字仅用于当前请求；默认不持久化原始菜单内容。若将来需要质量分析，先做最小化、脱敏并取得用户同意。

## 七、数据、质量与安全

### 数据分层

| 数据 | 来源与责任 | 是否可由 LLM 生成 |
|---|---|---|
| 食物营养与标准份量 | 食物数据台账、权威数据库、人工审核 | 否 |
| 食物别名与菜单语句 | 用户输入 + LLM 草稿 + 用户确认 | 可以提议，不能直接入库 |
| 动画路径与视觉规则 | 产品设计与代码 | 否 |
| 教育性解释 | 审核过的事实卡 + 受限 LLM 文案 | 可以改写，不可新增事实 |
| 医疗建议 / 风险结论 | 产品边界之外 | 否 |

### AI POC 的验收集（上线前必须有）

- 至少 30 条人工标注的中文菜单表达，包含份量模糊、同义词、混合菜、未知食物与否定表达。
- 观察四项：食物匹配是否正确、模糊时是否追问、用户是否接受草稿、是否出现无依据的健康表述。
- 硬性红线：模型不能给出医疗建议；未知项必须显式标记，不能编造数值。
- 失败体验：显示“我还没完全理解这顿饭”，一键回到手动选择，不阻断预演。

## 八、开源研究与可借鉴点

| 项目 | 它解决了什么 | FoodJourney 可借鉴 | 不应照搬 |
|---|---|---|---|
| [Open Food Facts / Product Opener](https://github.com/openfoodfacts/openfoodfacts-server) | 开放食品资料库、配料与营养信息 | 食物资料必须有来源、贡献与校验机制；数据是产品能力而非附属配置 | 直接复制其服务端或忽略其 AGPL / OdBL 许可、归因与回馈义务 |
| [Open Food Facts Swift](https://github.com/openfoodfacts/openfoodfacts-swift) | iOS 端查询、条码/手动输入与产品资料展示 | 条码可成为后续“包装食品 → 预演”的低摩擦入口；先显示数据再做解释 | README 标注维护者招募中，不把它当核心依赖；中国食物覆盖也需单独验证 |
| [AWS GenAI Food Analyzer](https://github.com/aws-samples/serverless-genai-food-analyzer-app) | 条码/图片识别 + 数据库事实 + LLM 解说 | “事实数据优先、LLM 做解释”；不同输出用途选择不同成本/速度的模型；结构化 JSON 比散文易消费 | 其账号、偏好、过敏与云服务架构超出 FoodJourney 当前阶段 |
| [AI4Food-NutritionDB](https://github.com/BiDAlab/AI4Food-NutritionDB) | 分层食物图像识别数据与基准 | 图像识别先做大类、再到食物；粒度越细准确率越低，因此照片识别必须要求用户确认 | 把研究数据集或模型当作中国菜品、份量和营养值的生产级答案 |

结论：已存在成熟的**食品数据、条码与图片识别**开源能力，但没有发现与 FoodJourney“可视化消化预演”完全同构的成熟开源产品。这是机会，也意味着不能把“识别出食物”误当成“能准确解释一个人的身体反应”。

## 九、待你确认的产品决策

1. 是否认可 AI 第一功能叫 **“AI 菜单翻译”**：先输入一句菜单，再确认后看动画？
2. AI POC 应放在 A 阶段录屏完成之后，还是与三食物 Demo 并行做一个仅内部可用的原型？建议前者。
3. 首版是否只支持文字输入；语音与拍照识别都延后？建议是。
4. 是否把“慢性病问卷”继续收敛为“我想优先了解的主题”，避免看起来像个人健康评估？建议是。
